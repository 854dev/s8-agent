# S8 보고 전 자기 검토

보고 직전에 리뷰어의 눈으로 실제 변경과 검증 근거를 확인한다. Projectman 워커라면 보고·후속 변경 기록 방법은 projectman-worker 스킬을 참고한다.

완료 기준은 Projectman 작업이면 승인된 계획과 completionCriteria, 그 밖에는 사용자의 요청과 대화에서 정한 기준이다.

## 1. 변경 전체 보기

- Git 저장소이면 `git status`와 `git diff`로 실제 변경을 확인하고 새 파일도 읽는다. Git이 없으면 변경한 파일·기존 내용과의 비교로 확인하며 Git 초기화를 요구하지 않는다.
- 디버그 출력, 주석 처리된 코드, 임시 파일, 관련 없는 서식 변경을 지운다.

## 2. 계획·완료 조건 대조

- 완료 기준 항목마다 그것을 만족시키는 변경과 증명하는 검증을 짝지어 본다. 짝이 없으면 미완료다.
- 요청 범위와 관계없는 자신의 변경을 정리한다. 기존 사용자·다른 작업의 변경은 되돌리지 않는다. 필요한 범위 변경은 매니저 또는 사용자와 조정한다.
- 계획이나 요청에서 정한 인터페이스(이름·시그니처·데이터 형식)를 그대로 지켰는가.

## 3. 결함 점검

- 경계 사례: 빈 값, 최대값, 중복, 동시 실행, 실패 후 재시도.
- 오류 처리: 삼킨 예외, 사용자에게 보이는 내부 오류, 정리되지 않는 자원.
- 보안: 신뢰 경계의 입력 검증, 경로 조작, 비밀정보 출력·기록, 권한 확인 누락.
- 테스트: 변경으로 생길 수 있는 회귀를 검증했는가. 테스트를 약하게 하거나 건너뛰게 바꾸지 않았는가.
- 환경변수를 바꿨다면 .env.example도 갱신했는가.

## 4. 검증 근거

- 완료 조건에 필요한 테스트·빌드 등 검증을 최종 변경 상태에서 실행하고 결과를 그대로 요약한다. 그 상태에서 이미 실행한 유효한 검증은 불필요하게 반복하지 않는다. commandNames의 이름 일치만으로 결과를 판단하지 않는다.
- 실패·미실행이 실제 완료 조건을 막는지 판단하고 검증 공백을 명시한다.

## 5. 보고 내용

- 무엇을 왜 바꿨는지, 사용자가 확인할 방법.
- 스스로 정한 것과 근거.
- 남은 일과 실제 장애를 숨기지 않는다.
- Projectman 워커라면 보고의 필드와 서버 검증 규칙은 projectman-worker 스킬을 참고한다.
