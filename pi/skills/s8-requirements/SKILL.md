# S8 요구사항 대화

사용자가 원한다고 믿는 것은 생각보다 얇다. 워커는 실행 중에 사람에게 묻지 못하므로, 지금 대화에서 "왜"까지 알아내야 워커가 사용자처럼 결정한다.

## 먼저: 무엇을 알고 있나

- 요청에 필요한 것이 다 있으면(예: "버튼 문구를 X로 바꿔") 묻지 말고 바로 초안을 쓴다.
- 중요한 것이 빠졌으면 대화를 시작한다. 첫 메시지는 두 가지뿐이다: 질문 없이 바로 초안을 원하면 그렇게 말해도 된다는 한 줄, 그리고 사용자가 장면을 묘사하게 하는 열린 질문 하나.

## 대화

- 메시지마다 질문은 하나, 한 문장으로 끝낸다. 텔레그램에서 읽기 쉽게 짧게 쓴다. 보기 목록은 사용자가 막혔을 때만 준다.
- 사용자가 말하게 한다. 정정할 수 있는 추측("X가 계속 문제라서 그런 거죠?")이 질문보다 나을 때가 많다.
- 다룰 영역(질문으로 읽어 주지 않는다): 무엇이고 왜 지금인가, 성공의 모습, 목표·비목표·실패 조건, 현재 상태와 시도한 것, 사용자가 신경 쓰는 세부.
- 어떻게 만들지(언어·라이브러리·구조) 중 사용자가 정할 것과 맡길 것을 일찍 가린다. 기존 코드가 있으면 그 방식을 따른다. 내가 정한 기본값은 소리 내어 말한다.
- 코드베이스 확인이 도움이 되면 무엇을 볼지 말하고 직접 read/grep으로 본다. 확인한 사실은 파일 경로와 함께 짧게 전한다.
- 제안 전에 여러 안을 혼자 비교하고 약한 안을 버린다. 비교표는 결정에 도움이 될 때만 보여 준다.

## 되읽기

한 부분을 설명할 수 있을 만큼 이해하면 짧게(텔레그램 기준 10줄 안팎) 되읽어 주고 틀리거나 빠진 것을 묻는다. 내 추측은 추측이라고 표시한다. 사용자가 말한 것만 사용자 결정으로 기록한다.

## 크기 정하기

이해가 끝나면 크기를 정해 말한다. 사용자가 바꿀 수 있다.

| 크기 | Projectman 등록 |
|---|---|
| 한 번의 실행으로 끝나는 변경 | task 하나 |
| 서로 의존하는 여러 기능 | 부모 task + subtask, 또는 dependsOn으로 순서 지정 |
| 독립된 여러 프로젝트 | 각각 따로, 순서를 합의하고 하나씩 진행 |

## 다음 단계

- 대화 결과는 s8-task-plan으로 실행 계획을 쓰고 s8-plan-review로 점검한다.
- 초안을 Projectman에 먼저 올려 두고 대화로 고쳐도 된다. 등록은 실행 승인이 아니다.
- 사용자 결정의 근거(대화 참조)는 decisionRefs에 남긴다.
- 사람이 계획을 확정하기 전에는 워커를 실행하지 않는다.
