# S8 계획 점검

확정 요청 전에 엔지니어링 관점으로 계획을 점검한다. 변경 규모에 맞춰 중요한 항목만 검토한다. 실행 중 새 사실이 나오면 매니저와 워커가 후속 판단을 조정할 수 있다.

## 근거와 쓰는 법

- 지적은 `파일:줄`과 짧은 문장 하나로 쓴다. 등급·점수 꼬리표는 붙이지 않는다. 중요한 것부터 쓴다.
- 판단의 근거가 된 코드 줄이나 계획 문장을 직접 읽어 확인한 것만 단정한다. 확인하지 못한 것은 문장 끝에 "확인 필요"를 붙이고, 단순한 의심은 버린다.
- 존재하는 코드와 계획이 제안한 코드를 구분한다. 아직 없는 코드를 관찰한 것처럼 쓰지 않는다.

## 0. 범위

- 각 하위 문제를 이미 해결하는 코드·라이브러리가 있는가.
- 목표를 이루는 최소 변경은 무엇인가. 미뤄도 되는 일과 범위 확장을 가린다.
- 결과가 독립적이거나 작업 간 충돌을 줄일 수 있을 때 분할을 검토한다. 파일 개수만으로 사용자 확인이나 분할을 강제하지 않는다.

## 1. 아키텍처

- 구성 요소 경계, 의존성, 결합도.
- 데이터 흐름과 단일 실패 지점. 흐름이 복잡하면 계획에 ASCII 다이어그램을 넣는다.
- 보안: 인증, 데이터 접근, API 경계, 비밀정보 취급.
- 새 경로·연동마다 현실적인 운영 실패 하나를 들고, 계획이 그것을 다루는지 본다.

## 2. 코드 품질

- 모듈 구조와 기존 패턴과의 일치.
- 오류 처리 공백과 빠진 경계 사례를 명시적으로 짚는다.
- 공통 코드 추출은 실제 호출자가 둘 이상이고 동작이 같을 때만 권한다. 비슷해 보이는 것만으로는 부족하다.
- 불필요한 추상화, 한 구현뿐인 인터페이스, 바뀌지 않는 값의 설정화를 걷어낸다.

## 3. 테스트

- 바뀌는 동작마다 실제 회귀를 잡을 테스트가 계획에 있는가. 테스트 개수는 목표가 아니다.
- 저장소의 테스트 프레임워크와 위치를 따르는가.
- commandNames가 completionCriteria를 증명하기에 충분한가.

## 4. 성능

- 반복 경로의 질의·호출, 무제한 조회·캐시, 타임아웃 없는 차단 호출, 파일 전체 적재.
- 규모(행 수, 요청 수, 바이트)를 적거나 모른다고 쓴다. 벤치마크 수치를 지어내지 않는다.

## 결과 처리

계획으로 해결할 수 있는 지적은 바로 반영한다. 사용자만 정할 사항은 필요한 판단과 근거를 모아 묻는다. 결정된 내용을 반복 확인하지 않는다. Projectman 계획 개정·사전 검토·실행 확정 방법은 projectman-manager 스킬을 참고한다.
