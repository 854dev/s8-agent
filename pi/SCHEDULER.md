# S8 스케줄러

S8 관리 대화의 `scheduler` 도구로 Projectman 예약을 관리하고, 별도 Node 프로세스가 예약 시각에 실행한다. 기존 셸 예약 실행은 유지하지만 관리 역할에서 셸 예약 생성·변경·삭제는 차단한다. Projectman 잡은 5분마다 조회하되 실행 가능한 워크·서브워크가 없으면 모델을 호출하거나 Telegram에 알리지 않는다. 운영체제별 cron 문법이나 패키지 없이 같은 스케줄러 코드를 사용한다.

## 실행

```bash
./start-pi.sh                    # 매니저 + 스케줄러 + 개발 슈퍼바이저
./start-pi.sh --no-scheduler     # 스케줄러 자동 시작 제외
./start-pi.sh --service scheduler            # 예약 데몬만 전경에서 실행
```

통합 실행은 기본 `s8-main` tmux 세션의 `scheduler` 창을 만들고, 재실행 시 정상 종료한 뒤 같은 창에서 프로세스를 교체한다. `--session 이름`을 지정하면 해당 런타임 세션에 같은 서비스 창을 연결한다. 매니저가 끝나도 예약 데몬은 유지된다. 제외 옵션은 이미 실행 중인 데몬을 종료하지 않는다.

`start-pi.sh --service scheduler` 단독 실행은 포그라운드 서비스다. 예약 실행을 유지하려면 macOS `launchd`, Linux `systemd --user`, Windows 작업 스케줄러 등 해당 OS의 서비스 관리자에 시작 명령을 등록한다. 여러 인스턴스가 동시에 시작되면 하나만 소유권을 얻고 나머지는 종료한다. tmux 세션의 정상 종료 신호(`SIGINT`, `SIGTERM`, `SIGHUP`)에는 실행 중 작업을 정리한 뒤 소유 잠금을 제거한다. 전원 종료나 강제 종료 등 신호를 처리하지 못한 비정상 종료 후 `.s8-runtime/scheduler/owner.lock`이 남으면 스케줄러가 실행 중이지 않은 것을 확인한 뒤 해당 잠금 파일만 제거한다.

Pi CLI와 인증정보는 `start-pi.sh`와 같은 `.pi-runtime`을 사용한다. `.env`는 시작 시 읽되 출력하거나 기록하지 않는다.

## 예약 CRUD

S8 대화에서 자연어로 `scheduler` 도구를 호출해 관리한다.

- `list`: 예약과 최근 결과 확인
- `create`: `id`와 잡 종류별 설정 필수. `kind=shell`(기존 기본값)은 `script`와 `time`(24시간 `HH:mm`) 또는 `intervalMinutes` 중 하나를 지정한다. 주기는 60을 나누어 떨어뜨리는 1~60분이며 `30`은 매시 :00·:30에 실행한다.
- `kind=projectman`: `projectUid` 필수, 주기는 `intervalMinutes=5`로 고정하고 `script`는 지정하지 않는다. 잡마다 지정 프로젝트만 조회한다.
- `timezone`은 IANA 시간대이며 기본값은 장비의 시간대
- `expiresAt`: 선택적 종료 시각. 명시적 시간대가 포함된 ISO 시각으로 지정하며 종료 시각부터 새 배치를 시작하지 않고 실행 중 배치에도 남은 시간을 한도로 적용한다. `null`로 제한을 해제할 수 있다. 기존 종료 시각 없는 예약의 동작은 유지된다.
- `update`: 종류, 프로젝트, 시각, 시간대, 활성화 여부, 종료 시각, 스크립트 변경
- `delete`: 예약과 스크립트 삭제

생성·수정·삭제에는 대화형 확인이 필요하다. 실행 상태와 예약은 `.s8-runtime/scheduler/`에 저장하고 Git에는 포함하지 않는다. 동시 수정용 `jobs.json.lock`이 비정상 종료로 남으면 Pi 작업이 끝난 것을 확인한 뒤 잠금 파일을 제거한다.

## Telegram 예약·배치 관리

메뉴의 `배치` 버튼 또는 `/jobs`로 목록과 마지막 실행 상태를 확인한다. 모델을 호출하지 않고 직접 처리하므로 Pi 응답 중에도 사용할 수 있다.

- `/jobs pause <id>`: 앞으로의 예약 실행 정지. 현재 배치는 계속 실행
- `/jobs resume <id>`: 예약 재개
- `/jobs stop <id>`: 현재 실행 중인 배치와 자식 프로세스 중단 요청. 앞으로의 예약은 유지

배치 중단은 이미 수행한 파일·DB 변경을 롤백하지 않는다. 종료된 데몬의 마지막 `running` 기록은 실제 프로세스 생존을 보장하지 않는다. 실행 취소 요청은 실행별 ID로 구분해 다음 배치에 적용되지 않도록 한다. Telegram에서 임의 스크립트 생성·삭제는 제공하지 않으며 기존 대화형 승인 정책을 유지한다.

## Projectman 지시 잡

- 5분 검사에서 지정 프로젝트의 활성 워크(`task`) 또는 서브워크(`subtask`) 1건만 선택한다. `ready`, `autorun=true`, `autorunMode=safe`, `risk=low`, `requiresApproval=false`, `allowedActions=[read]`, 발행 상태이며 예정 시각이 도래한 항목만 대상이다. 승인·검토·민감 태그는 제외한다.
- 기존 안전 정책을 확장하지 않는다. 현재 자동 프롬프트는 읽기 전용 조사만 지원하고 쓰기·배포 작업은 자동 실행하지 않는다. 서브워크는 부모의 활성화·권한도 확인한다.
- 서브워크가 있는 워크 전체를 한 번에 실행하지 않는다. 순서/단계와 기존 상태를 확인해 첫 미완료 서브워크만 선택하며 앞 항목이 `todo`, `blocked`, `review`, `doing`이면 이후 항목으로 건너뛰지 않는다. 부모를 자동 완료로 처리하지 않는다.
- 서버의 원자적 `ready → doing` 전환으로 선점한다. 하나의 UID에 동시에 두 프롬프트를 보내지 않는다. 아직은 직렬 실행이며 병렬 워커는 추가하지 않았다.
- 시작 알림이 Telegram API에 접수된 뒤 S8 Pi 읽기 전용 자식 프로세스에 정해진 프롬프트를 한 번 전달한다. 시작 알림이 실패하면 프롬프트를 실행하지 않고 기록을 남겨 다음 검사에서 재시도한다.
- 프롬프트 원문은 `pi/lib/projectman-dispatch.ts`의 `WORK_PROMPT`다. 지정 항목·프로젝트·부모 설명과 최근 Projectman 결과 기록을 전달하며 데이터로 취급한다. 기본 시간 한도는 3분, 항목의 설정은 최대 8분이며 운영 종료까지 남은 시간도 적용한다. 다른 작업·재귀 실행은 금지한다.
- 자식은 Pi JSON 이벤트 모드로 실행한다. `agent_settled`와 최종 공개 응답을 확인하며 프로세스 종료 코드만으로 성공을 판단하지 않는다. 강제 종료 때도 공개 텍스트·성공한 읽기 도구 경로를 체크포인트로 남긴다. 도구 본문·비공개 추론·인증 진단·원시 이벤트는 저장하지 않는다.
- 모델의 `completed` 결과는 기존 검토 정책에 따라 `doing → review`로 기록한다. `continue`, 시간·토큰 한도로 미완료인 결과는 수행 내용·남은 내용·다음 단계를 로그에 남기고 `doing → ready`로 전환해 다음 검사에서 한 번 더 진행한다. 수동 중단·사용자 판단 필요는 `blocked`로 남긴다.
- 로그는 Projectman이 원본이다. 새 프롬프트에는 선점 후 다시 읽은 최근 두 결과 로그의 끝부분을 담아 이력 증가로 인한 컨텍스트 누적을 제한하며 원본 로그는 삭제하지 않는다. 결과 출력은 최신 10,000자, 로그 결과는 최신 8,000자로 제한한다. 더 긴 기록은 원본 조사 자료와 함께 수동 확인한다.
- Telegram은 프롬프트 지시 시작과 실행 종료 결과만 보낸다. 완료·취소·승인 대기·비활성 항목의 단순 재조회는 무알림이다. 미완료 항목을 다음 프롬프트로 실제 재개할 때는 다시 시작·결과를 알린다.
- 결과 기록이 실패하면 `doing`을 임의로 재개하지 않는다. 실패·강제 종료 후에는 자식 프로세스 종료와 기록을 확인한 뒤 상태를 복구한다. 실행 중 `doing → ready`를 수동 강제 전환하지 않는다. 모델 종료 코드만으로 완료를 판정하지 않는다.
- 읽기 전용 프롬프트 자식은 기존 Linux/macOS 실행기를 재사용한다. 네이티브 Windows 실행은 지원하지 않으며 기존 쉘 잡은 Git Bash로 사용할 수 있다. macOS에서 부모가 강제 종료되면 독립 watchdog이 없어 고아 자식을 수동 확인해야 한다.
- `/jobs`의 `실행 idle`은 실행 가능한 항목이 없는 조회이며, `알림`은 마지막 실제 지시의 전송 상태다. 빈 조회는 이전 전송 실패를 덮어쓰지 않는다.

기존 잡 전환은 최신 데몬을 재시작한 뒤 명시적으로 실행한다.

```bash
node pi/bin/projectman-job.mjs <job-id> <project-uid>
```

- 잡의 활성화 여부·기존 종료 시각·작업 상태·결과 파일은 그대로 두고 종류와 조회 주기만 변경한다. 종료된 운영 기간은 자동 연장하지 않는다.
- 원래 쉘 스크립트는 롤백을 위해 유지한다. 롤백 전 잡을 일시정지하고 `scheduler update`로 `kind=shell`·스크립트·원래 주기를 확인한 뒤 재개한다. 잡 설정을 복원하기 전에 이전 데몬 코드로 되돌리지 않는다.
- Pi 대화의 새 CRUD 필드를 사용하려면 S8도 재시작한다. 이미 승인한 작업의 정책을 변경하거나 다른 프로젝트까지 조회 범위를 자동 확장하지 않는다.

## 스크립트와 Pi CLI

스크립트는 최대 8 KB이며 `<s8-agent>/.s8-runtime/scheduler/scripts/<id>.sh`로 저장한다. 각 스크립트는 현재 OS 사용자 권한으로 실행되므로, 예약을 만들기 전에 내용을 확인한다. S8이 생성한 스크립트는 사용자의 승인 후 예약 시각에 자동 실행된다.

예시 스크립트 내용:

```bash
#!/usr/bin/env bash
set -euo pipefail
"$S8_PI_BINARY" --print --no-session \
  --extension "$S8_PI_CONFIG_ROOT/extensions/projectman.ts" \
  --append-system-prompt "$S8_PI_CONFIG_ROOT/APPEND_SYSTEM.md" \
  'ph-projectman을 읽고 오늘 할 일을 우선순위와 함께 한국어로 요약해줘. 상태는 변경하지 마.'
```

스크립트 stdout/stderr 결과는 Telegram 대상이 설정되어 있으면 알림으로 전송한다. 봇 토큰은 환경변수 `TELEGRAM_BOT_TOKEN`에 유지하고, 저장소 루트 `s8-config.yml`의 `telegram.allowedUserIds`·`allowedGroupIds`·`scheduleChatId`로 허용 목록과 알림 대상을 지정한다. 대상 chat ID는 허용 목록 중 하나와 일치해야 한다. 파일이 없을 때만 기존 ID 환경변수를 사용하며, 파일이 있으면 누락된 값도 환경변수로 보충하지 않는다. 잘못된 파일은 시작 오류로 처리한다. 알림 대상을 지정하지 않으면 일반 예약 결과는 stdout에만 출력되며 부재중 운영 명령은 시작을 거부한다.

- 일시적 연결 오류·HTTP 429·5xx는 메시지 조각당 최대 3회 시도한다. 영구 오류는 재시도하지 않는다. 응답 유실 시 같은 알림이 중복 도착할 수 있다.
- 실행 결과와 알림 전송 상태는 별개다. `/jobs`는 `실행 success/failed`와 `알림 pending/sent/failed/not_configured`를 구분한다. 기존 기록은 `알림 미기록`으로 표시한다.
- `sent`는 Telegram API 접수 성공이며 실제 기기의 수신·읽음 확인은 아니다. 실패 원인은 HTTP 상태나 일반화한 연결 오류만 저장하고 알림 본문·인증정보는 상태 파일에 저장하지 않는다.
- 이 스크립트 결과 전송은 기존 쉘 잡의 호환 동작이다. Projectman 지시 잡에는 적용하지 않는다. 지시 잡의 빈 조회·승인 대기는 반복 알리지 않는다.

## Projectman 카운트 테스트

`pi/bin/count-test.mjs`는 지정 프로젝트의 차감 테스트만 수행한다. 일반 작업의 자연어 지시를 자동 실행하지 않는다.

```bash
node --env-file=.env pi/bin/count-test.mjs setup
node --env-file=.env pi/bin/count-test.mjs schedule <task-uid> '2026-10-14T09:00:00+09:00'
```

- `setup`: `854-workspace` → `100에서 출발해서 카운트하기` → 1·2·1000 차감 작업을 구성하고 `projectman-count` 30분 예약을 등록한다. 프로젝트 설명과 `attributes.minimumValue=0`에 결과 하한을 기록한다. 기존 미시작 3 차감 작업은 같은 UID로 1000 차감 작업으로 변경하며, 이미 시작했거나 차감 기록이 있으면 이관을 거부한다. 기존 결과와 예정 시각은 초기화하지 않는다.
- 작업의 `attributes.scheduledAt`은 처음에는 `null`이다. 위 `schedule` 명령으로 예정 시각을 지정하거나, S8의 Projectman `schedule` 도구로 변경할 수 있다. 작업을 시작한 뒤에는 시각 수정이 차단된다.
- 순서대로 하나씩 처리하며 첫 미완료 작업의 예정 시각이 도래하지 않으면 다음 작업도 기다린다. 09:10 예약은 스케줄러가 정상 실행 중일 때 09:30 검사에서 수행한다.
- 실행 전 프로젝트의 하한을 확인한다. `100 → 99 → 97` 뒤 1000을 빼면 -903이므로 파일을 변경하지 않고 작업을 `blocked`로 전환한다. 이유·예상 결과·건너뛰기 질문은 PH-CMS의 해당 작업 아래 `work_log`에 원자적으로 기록한다. 예약 결과 알림이 설정되어 있으면 기존 Telegram 알림 경로로 질문이 전달된다.
- 사용자가 대화나 Telegram에서 "1000 빼기는 하지 마라"라고 답하면 에이전트가 해당 작업을 확인하고 `projectman`의 `transition`으로 `blocked` → `canceled`, `event=updated`, 답변을 `message`에 기록한다. 다른 창구의 결정도 같은 전환으로 저장해야 한다. 임의 댓글·작업 설명만으로 취소를 추론하지 않는다.
- 수동 CLI에서도 `node pi/bin/count-test.mjs reject <task-uid> '1000 빼기는 하지 마라'`로 같은 결정을 남길 수 있다. S8이 시작 시 로드한 서비스 키 환경을 사용하며, 일반 사용자 셸에서는 별도로 환경을 준비한다. 이미 차감한 작업의 취소는 거부한다.
- 응답 대기 중에는 새 요청 로그를 반복 생성하지 않는다. 거부 결정은 세션 메모가 아닌 DB의 취소 상태·작업 로그에 남으며 다음 실행에서 취소 작업을 건너뛴다. 이 시나리오의 최종 값은 97이다. 즉시 재실행 트리거와 외부 창구의 자유문 답변 수집기는 별도로 제공하지 않는다.
- 단순한 "실행해도 된다"는 답변으로 결과 하한을 무시하지 않는다. 작업을 다시 실행하려면 규칙·작업을 명시적으로 수정한 뒤 별도로 재개해야 한다. 이전 1·2·3 시나리오는 실행기에서 계속 지원한다.
- `~/projectman-result.txt` 첫 줄은 `100`, 이후 줄은 `값<TAB>작업 UID<TAB>차감량<TAB>실행 시각`이다. UID가 이미 기록되면 차감하지 않고 Projectman 완료 처리만 복구한다.
- S8의 `PHCMS_ACCESS_TOKEN`에 설정한 서비스 키를 MCP 요청 헤더로 전달한다. MCP 서버에는 키를 저장하지 않는다. 수동 CLI는 위 명령처럼 S8 환경을 로드하고, 예약 실행은 스케줄러가 시작 시 로드한 환경을 사용한다. 쓰기 가능한 MCP 인증이 필요하다. 현재 테스트 CLI는 이 장비의 `http://100.120.50.80:3001/mcp`를 사용한다. 다른 장비에서는 이 주소를 바꾼다.
- 데몬과 테스트 실행기는 한 호스트에서만 운영한다. 다른 호스트의 별도 결과 파일과 실행을 조정하지 않는다. 비정상 종료 시 `projectman-result.txt.lock`이 남으면 실행기가 완전히 종료된 것을 확인하고 잠금 파일만 제거한다.

## 60분 부재중 카운트 운영

이 명령은 기존 쉘 방식의 카운트 테스트 전용이다. Projectman 지시 잡으로 전환한 이후에는 `away`로 기존 스크립트 실행을 다시 활성화하지 않으며, `scheduler`로 운영 종료 시각을 변경한다.

```bash
node pi/bin/count-test.mjs away <project-uid> 60
```

- S8이 로드한 환경과 최신 `start-pi.sh --service scheduler` 데몬이 필요하다. 종료 시각을 지원하지 않는 이전 데몬이면 먼저 재시작한다.
- 환경의 `TELEGRAM_BOT_TOKEN`과 공통 설정의 명시적 `telegram.scheduleChatId`로 실제 알림을 보내 확인한다. 알림 대상이 없거나 전달에 실패하면 운영을 시작하지 않는다. 일반 사용자 셸에서는 직접 환경을 준비해야 하며 에이전트가 환경 파일이나 키를 읽어 해결하지 않는다.
- `ready` 작업의 예정 시각을 운영 시작 시각으로 지정하고, 기존 `projectman-count` 예약을 5분 주기·활성 상태·시작 후 60분 종료로 설정한다. 한 검사에 작업 하나를 처리하며 검사는 매시 :00·:05·:10 등에 수행한다. 최대 대기 시간은 약 5분이며 즉시 첫 작업을 실행하는 명령은 아니다.
- `blocked`에서는 멈추고 질문을 알린다. 사용자 답변은 에이전트나 수동 `reject` 명령이 Projectman에 결정으로 기록해야 한다. 저장된 취소는 다음 5분 검사에서 반영하며 답변이 없다고 실행 허가로 간주하지 않는다.
- 종료 시각이 지나면 더 진행하지 않는다. 승인 대기 시간도 60분에 포함한다. 이후 답변은 기록할 수 있지만 자동 실행을 다시 시작하려면 새 운영 기간을 명시적으로 설정해야 한다.
- Telegram `/jobs`에는 종료 시각과 기간 종료 여부가 표시된다. 만료된 예약은 `/jobs resume`만으로 재개하지 못한다. 종료 시각을 갱신하거나 새 `away` 명령으로 기간을 지정한다.
- 이미 수행한 작업은 중단·만료로 롤백하지 않는다. 알림이 운영 도중 실패하면 요청 기록은 Projectman에 남지만 사용자가 즉시 수신했다고 보장할 수 없다.

## 제약

- 매일 `HH:mm` 또는 분 주기를 지원한다. 예약 시각에 스케줄러가 실행 중이 아니면 해당 실행은 건너뛰고 나중에 따라잡지 않는다.
- `.sh` 실행에는 Bash가 필요하다. Windows에서는 Git Bash 등 Bash를 PATH에 설치한다.
- 각 호스트에서 스케줄러 인스턴스 하나만 실행한다. 상태는 호스트별 로컬 런타임에 저장되며 다른 장치와 자동 동기화하지 않는다.
- 스크립트 출력은 Telegram으로 전송될 수 있으므로 비밀정보를 출력하지 않는다. 기본 redaction은 완전한 유출 방지책이 아니다.
